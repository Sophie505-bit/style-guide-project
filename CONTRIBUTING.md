# Как внести вклад в руководство по стилю

Спасибо, что хотите улучшить руководство. Документация — часть продукта,
и изменение правил проходит такой же путь, как изменение кода: ветка →
коммиты → Pull Request → ревью → merge → автодеплой.

## Как предложить изменение

1. **Проверьте, нет ли уже похожего предложения** в Issues и Pull Requests.
2. **Создайте Issue** с описанием проблемы: что не так, кого это затрагивает,
   какое правило мешает. Для мелких правок (опечатка, битая ссылка) Issue
   не нужен — сразу Pull Request.
3. **Создайте ветку от актуального `main`**:

   ```bash
   git switch main && git pull
   git switch -c docs/название-изменения
   ```

4. **Внесите правку**, при необходимости добавьте страницу и пункт в `nav`
   файла `mkdocs.yml`.
5. **Проверьте локально**: `mkdocs serve` и `npm run lint`
   (подробнее — [ниже](#как-запустить-локальную-сборку)).
6. **Закоммитьте** по правилам ниже и отправьте ветку:

   ```bash
   git push -u origin docs/название-изменения
   ```

7. **Создайте Pull Request** по шаблону репозитория, заполните чек-лист,
   дождитесь зелёного CI и пройдите ревью.

Типы веток: `docs/`, `fix/`, `ci/`, `chore/` — подробнее в разделе
[Ветки и Pull Request](docs/process/branches-pr.md).

## Требования к оформлению коммитов (Conventional Commits)

Формат: `<тип>(<область>): <описание>`.

Допустимые типы: `docs` (основной в этом репозитории), `feat`, `fix`,
`style`, `refactor`, `ci`, `chore`.

Правила:

- описание — с маленькой буквы, в императиве, без точки в конце, до 72 символов;
- область — раздел руководства: `tone`, `structure`, `accessibility`, `ci`;
- ссылка на задачу — в футере: `Closes #42`.

Примеры:

```text
docs(accessibility): добавить раздел о доступности текста
fix(links): исправить битую ссылку на глоссарий
ci: добавить проверку орфографии в workflow
```

Полные правила и антипримеры — в разделе
[Коммиты](docs/process/commits.md). При слиянии Pull Request выполняется
squash-merge, поэтому в `main` попадает один коммит с заголовком PR.

## Процесс ревью

1. Pull Request **нельзя** сливать без хотя бы одного approving review
   и зелёного CI.
2. Ревьюер отвечает в течение одного рабочего дня.
3. Комментарии оформляются метками: `blocker:`, `suggestion:`, `question:`,
   `nit:`, `praise:` — подробнее в разделе
   [Ревью документации](docs/process/review.md).
4. Автор отвечает на каждый комментарий: вносит правку или аргументированно
   отклоняет, затем делает повторный коммит:

   ```text
   docs(tone): ввести термин «учётная запись» по замечанию ревью
   ```

5. Все `blocker`-комментарии должны быть закрыты. После одобрения —
   squash-merge и удаление ветки.
6. Деплой запускается автоматически после merge в `main`; убедитесь,
   что workflow «Deploy to GitHub Pages» завершился успешно.

## Как запустить локальную сборку

Требования: Python 3.12+, Node.js 20+.

```bash
# Клонирование
git clone https://github.com/Sophie505-bit/style-guide-project.git
cd style-guide-project

# Зависимости Python и локальный сервер документации
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
mkdocs serve                     # http://127.0.0.1:8000

# Линтеры (второй терминал)
npm install
npm run lint                     # markdownlint + cspell
npm run lint:md -- --fix         # автоисправление оформления
```

Проверка сборки «как в CI» (то же выполняет workflow CI):

```bash
mkdocs build --strict            # падает на битых ссылках и проблемах nav
```

Что проверяет CI:

| Workflow | Проверка |
| --- | --- |
| `ci.yml` → markdownlint | Оформление Markdown |
| `ci.yml` → cspell | Орфография и терминология |
| `ci.yml` → `mkdocs build --strict` | Сборка, ссылки, навигация |
| `deploy.yml` | Публикация сайта после merge в `main` |

## Как добавить новый раздел

1. **Создайте файл** `docs/имя-раздела.md` (или `docs/группа/имя-раздела.md`).
   Имя — латиницей в `kebab-case`, без дат и версий.
2. **Начните файл с одного заголовка `#`** — он станет названием страницы:

   ```markdown
   # Доступность текста

   Правила, которые делают документацию удобной для всех читателей.
   ```

3. **Структурируйте раздел по шаблону руководства**:

   - назначение раздела — 1–2 предложения;
   - правила с уровнем обязательности (**MUST** / **SHOULD** / **MAY**);
   - примеры «плохо → хорошо»;
   - чек-лист для самопроверки, если правила прикладные.

4. **Добавьте страницу в навигацию** `mkdocs.yml` — без этого её не будет
   в меню:

   ```yaml
   nav:
     - Текст:
         - Доступность текста: text/accessibility.md
   ```

5. **Обновите перекрёстные ссылки**: из смежных разделов и, при
   необходимости, из глоссария.
6. **Проверьте локально**: `mkdocs serve` (страница в меню и открывается),
   `npm run lint`, `mkdocs build --strict`.
7. **Оформите Pull Request**: заголовок `docs(accessibility): добавить
   раздел о доступности текста`, в описании — ссылки на затронутые правила.

Если добавляете правило, которое можно проверить автоматически, — предложите
в том же PR настройку линтера (`.markdownlint-cli2.jsonc` или `cspell.json`).

Вопросы — в Discussions репозитория или владельцу раздела.
