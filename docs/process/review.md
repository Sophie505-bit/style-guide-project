# Ревью документации

Ревью — обязательный этап: ни один Pull Request не попадает в `main` без
хотя бы одного approving review.

## Кто участвует

| Роль | Задача |
| --- | --- |
| Автор | Подготовить PR, ответить на все комментарии |
| Ревьюер | Проверить соответствие правилам и точность фактов |
| Владелец раздела | Даёт финальное одобрение при изменениях правил |

Минимум один ревьюер, не являющийся автором. Для изменений в правилах —
два одобрения, одно из них — владелец раздела. **MUST**

## Что проверяет ревьюер

1. **Соответствие руководству** — пройдите по разделам: тон, терминология,
   типографика, структура, именование.
2. **Техническую точность** — команды и примеры выполнимы, факты верны.
3. **Полноту** — читатель сможет решить задачу, не задавая вопросов.
4. **Навигацию и ссылки** — страница добавлена в `nav`, ссылки живые.
5. **CI** — все проверки зелёные.

## Формат комментариев

Комментарии оформляются в стиле conventional comments: `<метка>: <текст>`.

| Метка | Значение |
| --- | --- |
| `blocker:` | Блокирует merge: ошибка в фактах, нарушение MUST-правила |
| `suggestion:` | Предложение, автор может принять или аргументированно отклонить |
| `nit:` | Мелочь, не влияющая на merge |
| `question:` | Вопрос по содержанию: почему так? |
| `praise:` | Отметить удачное место (не обязательно, но полезно) |

Примеры:

- `blocker: команда в шаге 3 не выполнится без флага --force; проверьте на стенде`
- `suggestion: термин «аккаунт» в п. 2 — по глоссарию должно быть «учётная запись»`
- `question: почему выбран HTTP-код 409, а не 422? это спорно при дубле заказа`
- `nit: пропущена запятая в перечислении`

## Правила тона на ревью

- Комментируйте текст, а не автора: «фраза допускает два толкования», а не
  «ты написал непонятно».
- Каждое замечание — с предложением, как исправить.
- Не требуйте личного стиля: если правило есть — ссылайтесь на правило,
  если правила нет — это `suggestion`, а не `blocker`.

## Обязанности автора

- Ответить на каждый комментарий: правкой или обоснованным отказом. **MUST**
- Не мержить с открытыми `blocker`-комментариями. **MUST**
- После правок сделать повторный коммит и повторно запросить ревью:
  «внёс правки по замечаниям, прошу посмотреть заново». **SHOULD**

## Сроки

- Ответ ревьюера — в течение одного рабочего дня. **SHOULD**
- Если ревью затянулось — напоминание в треде PR, затем — тимлиду
  или владельцу раздела.
