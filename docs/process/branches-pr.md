# Ветки и Pull Request

## Модель ветвления

- `main` — единственная долгоживущая ветка, всегда в рабочем состоянии;
  на её основе собирается опубликованный сайт документации. **MUST**
- Любое изменение — через отдельную ветку и Pull Request. Прямые коммиты
  в `main` запрещены (кроме исправления аварийной ситуации дежурным). **MUST**
- Ветка создаётся от актуального `main` и живёт не дольше одного спринта. **SHOULD**

## Именование веток

`<тип>/<краткое-описание>`, где тип — по разделу
[Именование](../naming.md):

| Тип | Назначение | Пример |
| --- | --- | --- |
| `docs/` | Новый раздел или правка правил | `docs/accessibility-section` |
| `fix/` | Исправление ошибки | `fix/broken-links` |
| `ci/` | Изменения линтинга и деплоя | `ci/add-spellcheck` |
| `chore/` | Обслуживание | `chore/update-mkdocs` |

## Жизненный цикл Pull Request

1. Создайте ветку: `git switch -c docs/accessibility-section`.
2. Внесите изменения; при добавлении страницы не забудьте про навигацию
   в `mkdocs.yml`. **MUST**
3. Проверьте локально: `mkdocs serve` и `npm run lint`. **MUST**
4. Закоммитьте по [Conventional Commits](commits.md).
5. Отправьте ветку: `git push -u origin docs/accessibility-section`.
6. Создайте PR по шаблону `.github/pull_request_template.md`; заполните
   чек-лист. **MUST**
7. Дождитесь зелёного CI: линтеры и сборка `mkdocs build --strict`. **MUST**
8. Пройдите ревью: минимум один approving review (см.
   [Ревью документации](review.md)). **MUST**
9. Выполните squash-merge; ветка удаляется автоматически. **SHOULD**
10. Убедитесь, что деплой прошёл: workflow «Deploy to GitHub Pages» завершён
    успешно, изменения видны на сайте. **MUST**

## Требования к PR

- Один PR — одна тема. Добавление раздела и переверстка всего сайта — разные PR.
- Заголовок PR — по Conventional Commits.
- В описании — ссылка на затронутые правила руководства и на issue, если есть.
- Изменения в PR не должны ломать сборку: красный CI останавливает ревью.
- Большой PR разбивается на части: проще ревьюить 2 маленьких, чем 1 на 1000 строк. **SHOULD**

## Что делать после merge

- Удалите локальную ветку: `git branch -d docs/accessibility-section`.
- Проверьте, что сайт обновился: статус деплоя в Actions → «Deploy to GitHub Pages».
- Если деплой упал — не правьте `main` напрямую: новая ветка `fix/deploy`.

## Частые ошибки

| Ошибка | Как исправить |
| --- | --- |
| PR с изменениями не от `main` | Обновите ветку: `git fetch && git rebase origin/main` |
| Страница есть, но её нет в меню | Добавьте пункт в `nav` файла `mkdocs.yml` |
| Красный markdownlint после push | `npm run lint:md -- --fix`, затем коммит `style: ...` |
| Конфликты в PR | Разрешите локально через rebase, запушьте force-with-lease |
